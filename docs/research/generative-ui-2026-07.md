# Research: generative UI representation for hirsel's deferred UI tier

Deep-research run 2026-07-09 (103 agents, adversarially verified claims). Recommendation feeds docs/SCOPE.md.

## Question

Best representation/architecture for "generative UI" in a personal agent chat client (2025-2026 state of the art): agent-authored HTML with custom components in sandboxed iframes (MCP-UI style), extended/structured markdown (custom directives or fenced component blocks), JSON component DSLs (Adaptive Cards, Slack Block Kit, Vercel AI SDK generative UI, A2A/AG-UI, Thesys C1, json-render), web components, or server-driven morphed HTML fragments (Datastar-style patch/morph over a socket). Context that constrains the answer: single-user personal agent system (hirsel); the agent itself authors and iterates UI templates as files in a git repo (self-hosting loop, templates parameterized with data at render time); client is a phone-first SolidJS PWA chat+inbox; server is a Rust host; transport is a custom WebSocket/iroh message stream with NO HTTP semantics (whatever format must be pushable as messages, support both append-once snapshots and update-in-place live views addressed by stable IDs); user interactions (taps, form submits) must flow back as chat messages; agent-generated content needs sandboxing (CSP, no external network); offline tolerance matters; no multi-tenant/permission concerns. Wanted: comparison of approaches on (1) LLM authoring reliability at generation time, (2) interactivity/event round-trip, (3) update-in-place semantics, (4) sandboxing/security, (5) fit with a custom non-HTTP message transport, (6) implementation effort in Rust+SolidJS; what real systems ship today (OpenAI Apps SDK / ChatGPT canvas widgets, Claude artifacts, MCP-UI spec status, Adaptive Cards adoption, AG-UI); and a concrete recommendation for hirsel's v1 of this tier.

## Summary

The 2025-2026 state of the art has converged decisively on one representation: pre-declared HTML/JS templates rendered in sandboxed iframes with a transport-agnostic JSON-RPC message bridge — standardized as MCP Apps (the first official MCP extension, declared production-ready 2026-01-26, carried into the 2026-07-28 MCP release candidate) and shipped by ChatGPT, Claude, VS Code Copilot, M365 Copilot, Goose, and Postman. The architecture maps onto hirsel unusually well: templates are registered ahead of time and parameterized with data at render time (matching the git-repo self-hosting loop), all UI-host communication is JSON-RPC 2.0 over postMessage with no HTTP semantics (relayable over the custom WebSocket/iroh stream), user interactions flow back through ui/message (posts a chat message) and ui/update-model-context (silent model-context sync), and security is iframe sandbox plus host-enforced CSP/permissions — no external network by default. The main verified alternative is the constrained JSON-component-DSL family (Vercel's json-render, Google's A2UI), which trades expressiveness for generation-time reliability via catalog+schema validation, and json-render ships an official @json-render/solid renderer with streaming JSON Patch updates. Recommendation for hirsel v1: adopt the MCP Apps shape without the MCP protocol — agent-authored HTML template files in git, rendered in sandboxed iframes (srcdoc + sandbox attr + strict CSP) in the SolidJS PWA, with a small ui/*-style JSON-RPC bridge whose messages the Rust host relays over the existing message stream; address live views by stable template-instance IDs and re-push parameter payloads for update-in-place. This buys maximum agent expressiveness (the agent iterates real HTML/CSS/JS, the thing LLMs author most reliably at template-development time rather than per-turn), standards-aligned semantics, and a migration path to real MCP Apps interop later; keep json-render/solid in reserve for cases where per-turn LLM-emitted UI (not pre-built templates) is needed.

## Verified findings

### Sandboxed-iframe HTML is the standardized representation for generative/agent UI: MCP Apps — the first official MCP extension, declared production-ready on 2026-01-26 and carried into the 2026-07-28 MCP release candidate — represents UI as server-provided HTML resources (ui:// URIs, MIME text/html;profile=mcp-app, declared in tool _meta.ui.resourceUri) that hosts render in sandboxed iframes. HTML is the only standardized content type; the spec explicitly did not adopt a JSON component DSL. MCP-UI's community patterns were folded into this spec and its SDKs are compliant with it.

- **Confidence:** high (3-0 across 5 merged claims [0,1,4,13,17])
- **Evidence:** Official MCP blog: 'The host fetches the resource, renders it in a sandboxed iframe, and enables bidirectional communication via JSON-RPC over postMessage'; MCP Apps is 'the first official MCP extension' and 'ready for production.' Normative spec mandates 'All View content MUST be rendered in sandboxed iframes.' SEP-1865 is status Final (Extensions Track) and 'unifies the approaches pioneered by MCP-UI and the Apps SDK into a single, open standard.' The 2026-07-28 RC post: 'MCP Apps lets servers ship interactive HTML interfaces that hosts render in a sandboxed iframe.' Nuance: it is an official optional extension, not core protocol.

### The interactivity/event round-trip is standardized as JSON-RPC 2.0 over postMessage with ui/*-namespaced methods plus shared MCP methods — pure message passing with no HTTP semantics, portable in principle to hirsel's custom WebSocket/iroh stream. Concrete methods cover the full loop hirsel needs: ui/initialize + ui/notifications/tool-input (init/data-in), ui/notifications/tool-result (host pushes results into the persistent iframe), tools/call (UI invokes tools), ui/message (widget asks host to post a chat message — exactly 'taps flow back as chat messages'), and ui/update-model-context (silent sync of UI state into model context, visible next turn). UI-initiated actions go through the same audit/consent path as direct tool calls, so there are no side channels. MCP-UI's legacy path (typed postMessage actions handled via onUIAction/onMessage) is the same transport-agnostic pattern.

- **Confidence:** high (3-0 on 7 claims, all unanimous [3,5,9,10,12,15,16,19])
- **Evidence:** Spec: 'MCP Apps use their own dialect of MCP, built on JSON-RPC like the core protocol... The transport is postMessage instead of stdio or HTTP' and 'You can implement the postMessage protocol directly... it's all standard web primitives' — a custom stack relays the same JSON-RPC payloads over its own channel. OpenAI docs: 'Use ui/message to ask the host to post a message' (role: user). RC post: 'every UI-initiated action goes through the same audit and consent path as a direct tool call.' Direction nuance: ui/update-model-context is UI-to-host state sync (latest snapshot overwrites), not an immediate chat message; host-to-UI update-in-place is served by streaming tool-results into the persistent iframe.

### The security model for agent-authored UI content across the ecosystem is iframe sandboxing plus host-enforced capability control: the sandbox blocks parent-DOM/cookie/localStorage access and parent navigation; the resource's _meta.ui declares a csp field (which external origins, if any, the app may load from — defaulting to none) and a permissions field for extra capabilities; hosts can restrict which tools an app may call. MCP-UI executes all content types in sandboxed iframes. This directly satisfies hirsel's no-external-network CSP requirement.

- **Confidence:** high (3-0 across 2 merged claims [6,11])
- **Evidence:** Spec verbatim: 'The sandbox prevents your app from accessing the parent window's DOM, reading the host's cookies or local storage, navigating the parent page, or executing scripts in the parent context'; _meta.ui carries 'csp to control what external origins the app can load resources from' and 'permissions'. MCP-UI README: 'In all content types, the remote code is executed in a sandboxed iframe' (nuance: for the legacy remote-DOM type, the script runs sandboxed but output renders as whitelisted host-native components).

### The standardized architecture is pre-registered templates parameterized with data at render time — a near-exact match for hirsel's planned git-repo template model. Tools declare UI templates ahead of time so hosts can prefetch, cache, and security-review them before anything runs; templates (presentation) are separated from tool results (data). Important reframing for the research question: in every shipped system, 'agent-authored HTML' means developer/agent-authored templates rendered per-invocation with data — the LLM does not stream raw HTML per turn. Hirsel's design (agent as its own template developer iterating files in git) is precisely this model with the agent in the developer seat, which also sidesteps per-turn LLM HTML-generation reliability concerns.

- **Confidence:** high (3-0 across 2 merged claims [18, plus verifier nuance on 14])
- **Evidence:** RC post verbatim: 'Tools declare their UI templates ahead of time so hosts can prefetch, cache, and security-review them before anything runs.' Spec overview: templates are predeclared ui:// resources referenced in tool metadata, declared 'upfront, during tool registration'; 'Templates (presentation) are separate from tool results (data).' Verifier note on claim 14: 'the HTML templates are developer-authored server resources parameterized with tool data — the LLM does not stream raw HTML per turn... matches hirsel's agent-as-template-developer design.'

### The strongest verified alternative is the constrained JSON-component-DSL approach, best represented by Vercel Labs' json-render: AI generates JSON specs validated against a developer-defined Zod-schema component catalog ('AI can only use components in your catalog'), with streaming/progressive rendering of partial specs via JSONL/RFC-6902 JSON Patch, a state model where interactions trigger actions (built-in setState re-evaluates dynamic bindings), and an officially published @json-render/solid renderer (v0.19.0, May 2026) that hirsel's SolidJS PWA could consume directly. This is the right tool when the LLM must emit UI per turn at generation time; it is weaker than templates for the agent-iterates-rich-UI use case since expressiveness is capped by the catalog.

- **Confidence:** high (3-0 on [20,22,23]; 2-1 on [21] (schema-conformance guarantee is vendor marketing))
- **Evidence:** README: 'Guardrailed - AI can only use components in your catalog'; 'JSON output matches your schema, every time' (treat 'every time' as vendor claim — validation catches hallucinated components/props, but reject/repair behavior on non-conforming output is undocumented); 'Stream and render progressively as the model responds'; 'The setState action updates the state model directly, which re-evaluates visibility conditions and dynamic prop expressions.' npm registry confirms @json-render/solid 0.19.0 published by Vercel release infrastructure. Pre-1.0, launched Jan 2026, 15.6k stars, active.

### Google's A2UI (v0.9, April 2026; v1.0 RC as of July 2026) is the second major JSON-DSL contender: a framework-agnostic, streaming-JSON standard for declaring UI intent where agents can only compose from a client-defined catalog of trusted, pre-approved components — 'a declarative data format, not executable code.' Its existence alongside json-render confirms the field has exactly two viable poles: catalog-constrained JSON DSLs (maximum generation-time safety/reliability, capped expressiveness) versus sandboxed-iframe HTML templates (maximum expressiveness, safety via sandbox rather than vocabulary restriction).

- **Confidence:** high (3-0 [24])
- **Evidence:** Google blog: 'a framework-agnostic standard for declaring UI intent... local or remote agents to communicate with any client application using a common language.' a2ui.org: the client 'maintains a catalog of trusted, pre-approved UI components... and the agent can only request to render components from that catalog'; flat streaming JSON structure designed for incremental LLM generation. Caveat: 'standard' is self-described (open v0.x spec), not standards-body ratified.

### Concrete v1 recommendation for hirsel: adopt the MCP Apps architecture shape without the MCP protocol itself. (a) Agent authors/iterates HTML+JS template files in the git repo (self-hosting loop = agent-as-template-developer, exactly the shipped industry pattern). (b) Rust host registers templates by stable ID and pushes render messages {template_id, instance_id, params} over the existing WS/iroh stream; re-pushing params to the same instance_id gives update-in-place live views, append-once snapshots pin a params payload. (c) SolidJS PWA renders templates in sandboxed iframes (sandbox attribute + strict CSP meta blocking all external origins; templates cacheable by the service worker for offline). (d) A small ui/*-style JSON-RPC bridge over postMessage carries taps/form-submits up; the client wraps ui/message payloads as chat messages on the stream — matching the standardized round-trip semantics one-to-one. This scores best across all six comparison axes given hirsel's constraints, keeps interop optionality with real MCP Apps, and json-render/solid remains available as a complement for per-turn LLM-emitted UI.

- **Confidence:** high (synthesis of unanimous findings 1-6)
- **Evidence:** Every load-bearing element is independently verified above: HTML-templates-in-sandboxed-iframes is the ratified, multi-vendor-shipped representation (findings 1-2); the bridge is explicitly transport-agnostic JSON-RPC message passing with the spec inviting direct implementation over other channels (finding 3); sandbox+CSP satisfies the no-external-network requirement (finding 4); predeclared-template-parameterized-at-render-time is the spec's own architecture and matches the git-repo loop (finding 5). The single-user, no-multi-tenant context removes the consent-UI overhead that motivates much of MCP Apps' audit machinery, so the bridge can be minimal (render, event, update-context, post-message). Implementation effort is modest: Rust side is message routing plus template file serving; SolidJS side is an iframe wrapper component plus a postMessage relay.
