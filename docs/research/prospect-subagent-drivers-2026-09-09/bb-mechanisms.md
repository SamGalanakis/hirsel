## What bb actually runs

bb's host runtime speaks its own JSON-RPC provider-bridge protocol to a plugin-owned bridge. The Codex bridge starts an app-server child per resident thread and translates Codex messages into semantic deltas. The Claude bridge uses the **Claude Agent SDK** `query()` with an async input iterator; that SDK controls the Claude CLI. Its optional recording mode takes over the SDK's `spawnClaudeCodeProcess` hook. This is not evidence to replace Hirsel's native Rust driver seam: transfer the lifecycle and acceptance invariants, not the SDK/plugin stack.

## Transferable mechanisms, ranked

1. **Correlate command results separately from streamed work.** Codex connection keeps a request-id map; responses resolve/reject precisely that request, validate the supplied result schema, and optionally time out. Child exit rejects all outstanding requests. The bridge awaits `initialize` before constructing the thread, and awaits turn/interrupt responses before reporting command success. Evidence: [`app-server-connection.ts:138-145,234-257,330-373`](https://github.com/get-bb/bb/blob/4ed2743219e8a6ecd7d2c2535c68865dcf821b20/plugins/provider-codex/src/bridge/app-server-connection.ts#L330-L373), [`bridge.ts:856-865`](https://github.com/get-bb/bb/blob/4ed2743219e8a6ecd7d2c2535c68865dcf821b20/plugins/provider-codex/src/bridge/bridge.ts#L856-L865), [`bridge.ts:1469-1496`](https://github.com/get-bb/bb/blob/4ed2743219e8a6ecd7d2c2535c68865dcf821b20/plugins/provider-codex/src/bridge/bridge.ts#L1469-L1496).

2. **Make in-flight input semantics explicit.** Codex `turn/steer` sends `expectedTurnId`; only its successful response produces `input.accepted` for the originating `clientRequestId`. The protocol distinguishes live injection from prompt-boundary queuing using `steerMode`. Claude `pushInput` rejects on a closed stream and resolves when its async iterator consumes the message; the bridge awaits that before emitting acceptance. This Claude guarantee is SDK consumption, not proof that the model has read the input. Evidence: [`bridge.ts:1500-1540`](https://github.com/get-bb/bb/blob/4ed2743219e8a6ecd7d2c2535c68865dcf821b20/plugins/provider-codex/src/bridge/bridge.ts#L1500-L1540), [`protocol:80-99`](https://github.com/get-bb/bb/blob/4ed2743219e8a6ecd7d2c2535c68865dcf821b20/docs/provider-bridge-protocol.md#L80-L99), [`sdk-session.ts:296-330,376-425`](https://github.com/get-bb/bb/blob/4ed2743219e8a6ecd7d2c2535c68865dcf821b20/plugins/provider-claude-code/src/bridge/sdk-session.ts#L296-L330), [`Claude bridge.ts:2688-2700`](https://github.com/get-bb/bb/blob/4ed2743219e8a6ecd7d2c2535c68865dcf821b20/plugins/provider-claude-code/src/bridge/bridge.ts#L2688-L2700).

3. **Supervise process exit and protocol settlement as different facts.** Codex finalization waits for stdio `close` but starts a bounded grace timer on `exit`; it rejects pending RPCs and calls exit handling even on status 0. The bridge fails every still-open provider turn with exit details. Interrupt waits a bounded interval for actual turn settlement, synthesizes interrupted settlement if necessary, clears remaining item state, releases the session, then responds. Evidence: [`connection.ts:192-219,313-323`](https://github.com/get-bb/bb/blob/4ed2743219e8a6ecd7d2c2535c68865dcf821b20/plugins/provider-codex/src/bridge/app-server-connection.ts#L313-L323), [`bridge.ts:791-827`](https://github.com/get-bb/bb/blob/4ed2743219e8a6ecd7d2c2535c68865dcf821b20/plugins/provider-codex/src/bridge/bridge.ts#L791-L827), [`bridge.ts:1569-1608`](https://github.com/get-bb/bb/blob/4ed2743219e8a6ecd7d2c2535c68865dcf821b20/plugins/provider-codex/src/bridge/bridge.ts#L1569-L1608).

4. **Own children from spawn through failed construction.** Codex bridge attaches the child connection to its session before initialization; construction catch removes the session and awaits child kill. The connection immediately installs output/exit listeners and retains a bounded stderr tail. Evidence: [`bridge.ts:985-997`](https://github.com/get-bb/bb/blob/4ed2743219e8a6ecd7d2c2535c68865dcf821b20/plugins/provider-codex/src/bridge/bridge.ts#L985-L997), [`bridge.ts:1077-1085`](https://github.com/get-bb/bb/blob/4ed2743219e8a6ecd7d2c2535c68865dcf821b20/plugins/provider-codex/src/bridge/bridge.ts#L1077-L1085), [`connection.ts:131-159`](https://github.com/get-bb/bb/blob/4ed2743219e8a6ecd7d2c2535c68865dcf821b20/plugins/provider-codex/src/bridge/app-server-connection.ts#L131-L159).

5. **Test the native wire boundary, including adversarial process behavior.** A real Node child fixture exits while a descendant holds stdout and emits a late response; the transport test verifies that final response and the original exit status survive. Other cases cover EPIPE ordering and immediate broken-stdin termination. Codex recorded-conformance runs every applicable recorded matrix cell and asserts no failures. Shared semantic conformance includes accepted-turn settlement, zero-work settlement and stop settlement before response. Evidence: [`connection.test.ts:47-101`](https://github.com/get-bb/bb/blob/4ed2743219e8a6ecd7d2c2535c68865dcf821b20/plugins/provider-codex/src/bridge/app-server-connection.test.ts#L47-L101), [`recorded-conformance.test.ts:1-12`](https://github.com/get-bb/bb/blob/4ed2743219e8a6ecd7d2c2535c68865dcf821b20/plugins/provider-codex/src/bridge/bridge.recorded-conformance.test.ts#L1-L12), [`conformance/scenarios.ts:912`](https://github.com/get-bb/bb/blob/4ed2743219e8a6ecd7d2c2535c68865dcf821b20/packages/provider-bridge-protocol/src/conformance/scenarios.ts#L912), [`scenarios.ts:1147`](https://github.com/get-bb/bb/blob/4ed2743219e8a6ecd7d2c2535c68865dcf821b20/packages/provider-bridge-protocol/src/conformance/scenarios.ts#L1147).

## Hirsel review through these rules: four strongest candidates

### BB-1: Pipe write success currently substitutes for provider command acceptance

Hirsel `codex.rs:92-103` sends initialize then thread/start without awaiting initialize. `read_codex_thread_id` (`:296-317`) extracts a thread id but does not reject matching RPC errors. `prompt` (`:136-145`) and `interrupt` (`:147-166`) return `write_json_line`'s flush result. The reader (`:319-390`) only extracts turn IDs, progress, and terminal notifications; an RPC `error` response produces no command failure. The host directly propagates those write-only results (`tools/subagents.rs:109-140`). A provider-rejected start/prompt/interrupt can therefore be reported as successfully submitted while doing no requested work; startup rejection degrades into the generic 30-second missing-id timeout.

Recommended outcome: a small native request/response dispatcher with pending IDs, result validation for consumed fields, explicit provider errors, bounded command waits and rejection on transport closure. Sequence startup from successful initialize. Keep command acknowledgement distinct from eventual work completion. Apply equivalent request correlation to Claude control responses where its wire supports them (`claude.rs:121-138` sends request ids, `:214-245` ignores control-response messages). Do not claim `initialized` omission is a bb-derived defect: the inspected bb initialization path also does not send that notification.

Verification case: fake native peer returns JSON-RPC error for thread/start or interrupt; caller must receive that error promptly and initial spawn must not leave a tracked running process. Interleave a server-initiated request with the same numeric id to verify method-based direction discrimination.

### BB-2: Codex follow-up input has no explicit steering contract

The public tool promises follow-up input to a running process (`lash_runtime/tool_defs.rs:252-254`). Codex `prompt` always sends `turn/start` (`codex.rs:136-145`), despite tracking an active turn id. bb has a separate `turn/steer` operation with `expectedTurnId` and accepted-input correlation. Hirsel's host retires the session on its first terminal event (`tools/subagents.rs:89-99`), so a follow-up held for a later turn is especially hazardous: the host can retire that child at the current turn boundary before subsequent work is consumed.

Recommended decision: define `subagents.prompt` as steering the currently running turn, and use Codex `turn/steer` with the current provider turn id; report an explicit stale/not-running result when the target finishes. Alternatively expose intentional queue semantics, but then track accepted queued input and revise retirement policy. The first option fits current one-process-until-terminal behavior with less machinery. Claude's native behavior needs its own confirmed acceptance contract; do not assume equivalence from its pipe write.

This is a mechanism/contract mismatch, **not a claim that a particular current Codex version necessarily rejects turn/start while busy**. Verify installed-protocol behavior or a pinned CLI fixture before selecting the implementation. No automatic resume/restart is proposed (ADR 0004).

### BB-3: Clean child exit without a terminal leaves work unsettled; inherited stdout can postpone exit detection indefinitely

Shared `finish_child` (`shared.rs:172-191`) has `Ok(status) if terminal_sent || status.success() => {}`. Thus status 0 without a terminal emits nothing. Both native readers call it only after stdout EOF (`codex.rs:326-390`; `claude.rs:156-200`). A descendant retaining the stdout fd can keep the reader awaiting EOF even after the direct child exits. Host retirement/wake is terminal-event-driven (`tools/subagents.rs:71-99`), so these paths can strand a running process and its addressed work. `EventHub` still has a sender held by the driver registry, so reader completion alone does not close the subscriber stream.

Recommended outcome: one supervisor races child wait with stdout drain, gives final bytes a bounded grace interval, and emits exactly one terminal failure whenever the accepted work lacks provider settlement, irrespective of exit code. Include a bounded stderr tail in the reason. Preserve the existing group kill on retirement; this is the missing path **to** retirement, not a request to add already-existing cleanup.

Verification cases: silent `exit 0`; failed exit after valid terminal (no duplicate); direct child exits while descendant retains stdout; final terminal bytes arrive during allowed drain grace. bb's exit fixture gives a concrete template.

### BB-4: Codex startup acquires process-group ownership too late

`codex.rs:75` spawns a new session/process group, but the RAII `ProcessGroup` guard is constructed only at `:115`, after initialization writes and the 30-second thread-id wait (`:92-103`). Those fallible awaits can return or be cancelled while the child exists but no cleanup guard does. `start_in_process_group` (`shared.rs:136-145`) sets `setsid`; it does not set Tokio `kill_on_drop`. Stderr is piped at spawn but draining starts only at `codex.rs:131`, after startup completes. A startup that fills stderr can therefore block before the response Hirsel awaits. Existing `drains_spawned_cli_stderr_without_deadlock` (`tests.rs:324-343`) validates the drain helper, not its placement in the native startup path.

Recommended outcome: establish process-group ownership immediately after spawn, start stderr draining immediately, and make construction transactional through handle publication. On startup rejection, timeout or cancellation, close input, kill owned descendants and reap the child. Keep bounded diagnostics for startup errors. bb's explicit construction catch is a transfer example; Rust can express the invariant with a guard.

Verification cases: native fake child never answers initialization and spawns a descendant; cancel startup; fake writes more than pipe capacity to stderr before responding; initial turn write fails after registry insertion. Observe only newly spawned fixture pids, never user's live sessions.

## Test delta and considered-but-not-adopted

Hirsel already has fake-driver fixtures, helper tests, ignored live Claude/Codex smoke tests (`tests.rs:345-390`) and a real-subagent e2e script that exercises Codex fixing a Python test and interrupting a long process. This review does **not** rediscover these as absent. The useful delta is a hermetic fake **native CLI** wire harness through `CodexDriver`/`ClaudeCodeDriver`, plus sanitized trace fixtures to detect protocol drift without spending tokens. Use the four candidate failure modes as assertions, not a generic test-count goal.

Do not copy bb's plugin architecture, timeline vocabulary, SDK dependency, automatic session rebuild/retry behavior, or large recovery state machine. Native Rust drivers and current Thread ownership are settled. bb's request helper only adds a timeout when a caller passes one, and many mutation responses intentionally use `z.unknown()`; it is not evidence for universal full-result validation. Its Claude input acknowledgement means SDK iterator consumption, so adopting its surface language without checking Hirsel's native echo/control protocol would overstate the guarantee. bb's docs state stronger cross-provider settlement invariants than this scoped reader has re-derived for every Claude path; the clean-exit counterexample above uses directly inspected Codex implementation, not an unverified blanket claim of Claude superiority.
