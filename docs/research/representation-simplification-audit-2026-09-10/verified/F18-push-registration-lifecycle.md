# F18 — delivery registration does not follow token refresh or survive history reset

Recommend; high confidence, medium priority. Canonical owner C22 registration lifecycle; independent C25 reset finding is consolidated here, not a second issue. Workers ../workers/C22-FFI-ANDROID.md F2 and ../workers/C25-HOST-OPS.md C25-02. Independently reopened onNewToken, MainActivity registration effect, settings preference, core register/flush path, Storage::reset, push_tokens schema/upsert and sender enumeration.

Two real transitions violate one history-independent delivery-registration contract. (1) Android registers T1; Firebase calls onNewToken(T2) while connection.isOnline stays true. Callback only logs, no state/write changes, and the effect keyed only on isOnline never registers T2. (2) History reset deletes push_tokens while preserving authenticated device credentials/connection; no client re-registration occurs on that history change, so new-history deliveries have no recipient. Neither requires malformed input.

Target: keep delivery registration outside conversation history, preserving existing push_tokens rows across history reset; publish the current Android token/preference through one observable durable owner and register that current value whenever token, enabled preference or online connection changes. Callback records new token, offline changes defer until an authenticated connection is available; do not create an ad hoc second socket from the callback. Preserve disabled-notification behavior and never log token values. Use existing registerPushToken API/table, no new host current-token column or wire contract. Scope Android service/state/root effect plus the one Storage reset deletion and meaningful lifecycle tests. Do not conflate host registration retention with restarting any work.

Required validation: T1 registration then callback T2 without reconnect sends T2; refresh offline registers latest when online; preference off/on triggers intended registration; history reset retains registered push token and a new needs-owner delivery can use it. Preserve history-bound push destinations (F17), stale notification rejection and existing auth/device credentials. Root may split implementation across Android and reset files but should retain this one canonical lifecycle finding. Audit ran no tests/live reads.

Coordinator reran the C22 onNewToken/fetchFcmToken/registerPushToken/pushEnabled/connection.isOnline query across Android, FFI and client core: 20 matching lines. Reopened the exact MainActivity registration effect and logging-only callback at fixed HEAD.

Independent materiality qualification: the existing host registry is keyed by token (push_tokens.rs upsert conflicts on token), with no device key. It is not a per-device current-token replacement/revocation model; preservation and registering a refreshed token do not remove older tokens. Keep that existing scope. Android owns durable observable latest token and enabled preference; off retains current local notification suppression, on/refresh/online register the latest token. No host device-schema redesign.
