# Side Chats: seeded forks that produce the Owner's reply

An Inbox Item can be opened into a Side Chat — an ephemeral conversation scoped to that item, rendered as a sheet over the main Chat. Three decisions define it. (1) The fork is a *seeded scope*, not a transcript copy: a fresh lash session seeded with the agent prompt, the item + its anchor exchange, and a bounded window of recent chat — deterministic and host-built, no main-agent turn spent opening one. (2) The Conclusion is the Owner's reply, not the Agent's: concluding has the side agent draft, the Owner edit/confirm, and the result lands in main Chat as the Owner's anchor-refed reply — the main Agent reacts to it like any Quick Reply and never sees the side transcript. The side chat is a fancy reply composer; the main loop gains no new semantics. (3) Side sessions are ephemeral cattle: concluding archives the item and discards the session; topics that outgrow a side chat graduate to the main conversation. Consequence: the client protocol drops its "exactly one session" assumption — frames gain an optional side-chat scope (protocol v2), which is the deliberate cost, paid now because multi-surface streams are needed later anyway (UI templates tier). The Inbox surface also moves from a separate tab into a Tray under the Chat; the Inbox tab is removed.
