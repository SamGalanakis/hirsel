# Native mobile apps on a shared Rust client core; Android first; web becomes the desktop client

The mobile end-state is a native app, not the installed PWA: hirsel is the Owner's highest-frequency personal surface and a chat app — exactly where native earns its keep (keyboard/scroll/haptics, real push, ongoing-notification process status, and eventually a hole-punched direct iroh connection that no browser can do). Shape: a shared **`hirsel-client-core`** Rust crate owns everything below the skin — protocol client, reconnect/offline queue, local store, and later the iroh transport — exposed via uniffi; native UIs are thin skins over it (**Android first**: Jetpack Compose, sideloaded APK, FCM push via a new host gateway; iOS later: SwiftUI over the same core, APNs). The web client is NOT deprecated: it remains the desktop client and the protocol's reference implementation. Two frontends stay sustainable because the wire protocol is the contract (small, versioned, mirrored, runbook-gated) and the Rust core absorbs most protocol evolution. Cost accepted: native lags web on new features; the discipline is that anything transport/state-shaped goes in the core, not the skins.

Considered and deferred (2026-07-10): a Slack bot as an ADDITIONAL bridge surface — Socket Mode fits the no-open-ports constraint, threads map to Side Chats, Block Kit to Quick Replies, and push comes free; rejected as the primary interface because it caps the product at Block Kit (no turn timeline, no CLI composer semantics, no generative-UI tier) and routes everything through Slack's cloud. Remains a potential future entrypoint: the host's product-state surface is adapter-shaped, so a slackbot would be a contained addition, not a rewrite.
